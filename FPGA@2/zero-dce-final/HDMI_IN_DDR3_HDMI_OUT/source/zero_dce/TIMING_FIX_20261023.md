# 2026-10-23：PW 读出路径时序修复

## 使用的报告

`report_timing/HDMI_IN_DDR3_HDMI_OUT_top.rtr`，报告头时间 **2026-10-22 17:48:02**，PG2L100H-6FBG676 / PDS 2023.2-SP4。像素时钟周期为 6.7273 ns。

- 像素域 slow setup：WNS **−0.930 ns**，TNS **−12.989 ns**，**24** 个失败端点。
- 同域 fast setup：WNS +1.629 ns，0 个失败端点。
- slow/fast hold、recovery、removal 和脉宽汇总均未显示失败端点。
- 报告仅展开像素域最差的 3 条 setup 违例，不能据此声称已检查全部 24 个失败端点。

## 根因与修改

展开的路径均由 `core/depth_*_lower` 的级联 DRM 读口，经 `depth_q`，直接进入八路 PW APM 乘法器输入。三个 slack 分别为 −0.930 / −0.815 / −0.778 ns。最差路径包含 RAM 及级联输出约 1.816 ns、8 负载共享数据网布线约 3.947 ns、APM 输入 setup 1.494 ns，clock skew 为 −0.250 ns。问题主要是 RAM 到乘法器之间的长距离共享布线，不是 OSD 十进制文字路径。

仅修改 `zdce_cnn_core.v`：

1. RAM 读出之后增加 `pw_input` 寄存器，并加 `syn_preserve/syn_keep` 保留属性，使 RAM 读出与 MAC 运算分属两个周期。
2. 八路 `pw_weight_i`、打包偏置 `pw_bias_i` 与数据同拍寄存；`pw_valid_i/pw_first_i/pw_last_i` 同样延迟一拍。乘法只使用本拍对应的输入和权重，首次累加仍使用该组原有偏置。
3. `PW_DRAIN` 原本等待真实的 `pw_valid_m && pw_last_m`，继续使用该条件，自动等待新增流水。最后一个输入通道必须实际进入累加器后才进入保存状态。
4. 保留此前 PW 写回寄存和 `PW_FLUSH`、DW 输入/量化流水、Tanh 流水；未改网络、权重、量化、特征 RAM 容量、8 路 MAC 数量及视频接口。

新增名义寄存位为输入 16 + 权重 128 + 偏置 256 + 控制 3 = **403 bit**，实际可能打包或优化，按综合报告确认。没有新增 RAM、乘法器或 DDR 流量。保留属性是否生效、寄存器最终位置及拆分后裕量必须从新报告确认，不能仅凭源码认为已经收敛。

## 周期影响

每个网格像素有 6 层×4 group + 最终层 1 group = 25 个 PW group，新增一级后各多一拍排空，共 **540×25 = 13,500 周期/帧**。

- DW：1,414,295 周期，未变化。
- PW/保存/激活：540×1254 + 6 = 677,166 周期。
- 合计 **2,091,461 周期，14.084 ms @148.5 MHz**，相对 2,475,000 周期/帧预算余量约 15.5%；启动、排队、帧边界发布仍另计少量周期。
- 视频仍每拍一像素，CNN/OSD 固定 32 拍，不含板级输出最后一拍；KEY1/KEY2、RGB 文字和网格不变。

## 验证边界

本次未修改 PDS 或原 FDC，未运行 HDL 仿真、综合、布局布线或上板测试。用户重新实现后应检查新的全部失败端点、保留寄存器和 RAM→寄存器→MAC 路径，而不只查看 WNS。

本报告仍把 `pixclk_in` 按 **1000 ns** 分析。对于 1080p60，已有 `source/zero_dce/hdmi_rx_clock.fdc` 中的 6.734006 ns 显式时钟需要由用户加载，或在实际使用的约束里等效修正；只保留一份正确显式约束。HDMI 输入/输出延迟也需要按板级参数补充。不能用当前输入域的大正裕量作为 1080p60 接口通过的依据，不能用 false path 或放宽时钟代替本次数据通路修复。
